1. Introduction

This assignment studies how a community hall can choose between overlapping booking requests. Each request has a start time, finish time and fee. Bookings may touch at an endpoint: a request ending at 12 and another starting at 12 are compatible. The goal is to maximize total fee while accepting only compatible requests.

2. Implementation

2.1 Greedy rules

The earliest-finish rule sorts bookings by finish time and takes each request that fits after the last accepted booking. The highest-fee rule considers the largest fees first and accepts a request only when it does not overlap any booking already selected. Both return the total fee and original request indices.

2.2 Dynamic programming

The optimal method sorts by finish time. For each request j, binary search finds p(j), the number of earlier requests that finish no later than j starts. It compares skipping j with taking j and adding the best compatible prefix:

OPT(0) = 0;   OPT(j) = max(OPT(j - 1), feej + OPT(p(j)))

The selected indices are reconstructed by following the recorded take-or-skip decisions. A brute-force method checks every subset and is limited to at most 15 requests for verification.

3. Testing

The tests cover no requests, one request, all-overlapping requests, non-overlapping requests, back-to-back requests, the supplied example, and counterexamples for both greedy rules. Dynamic programming was compared with brute force on 500 seeded random inputs of 0 to 10 requests. A separate property check confirmed that earliest finish is optimal by total fee when all fees are equal. All ten test groups passed.

Supplied example: earliest finish returns (7,500, [0, 3, 4]); dynamic programming returns (10,000, [1, 4]). The highest-fee rule also returns (10,000, [1, 4]) for this particular input.

4. Greedy Counterexamples

4.1 Earliest finish

For requests `[(0, 4, 12), (0, 2, 5), (2, 4, 5)]`, earliest finish selects indices [1, 2] for a fee of 10. The optimal choice is index [0], earning 12. Choosing the shorter events maximizes the number of bookings, but not their total fee.

4.2 Highest fee

For requests `[(0, 3, 10), (0, 1, 6), (1, 3, 6)]`, highest fee selects index [0] for 10. The optimal schedule is [1, 2], earning 12. Taking the single most expensive request blocks two compatible bookings with a larger combined fee.

5. Why the DP recurrence is correct

Consider an optimal schedule among the first j bookings in finish-time order. It either excludes booking j, in which case its best fee is OPT(j - 1), or includes it. If j is included, every other selected booking must finish by its start, so the best compatible earlier schedule has value OPT(p(j)). These two cases cover every feasible schedule. Taking the larger value therefore gives the optimum for each prefix, and following the recorded choices reconstructs an optimal set.

8. Critical Reflection

What do successful tests say about correctness? Passing tests increases confidence but does not prove a greedy rule is optimal. My counterexamples use only three requests and show how a locally reasonable choice can block a more valuable combination.

Should the manager keep a simple rule? When fees differed, earliest finish averaged 79.90% of the optimum and highest fee averaged 87.09% over the 1,000 test cases. Their worst results were lower still. If maximizing revenue matters, the DP method avoids relying on a heuristic.

Why does earliest finish work for equal fees? Every accepted request then contributes the same fee, so maximizing total fee is the same as selecting the largest number of compatible requests. Earliest finish leaves as much room as possible for the remaining requests.

9. Conclusion

Earliest finish is optimal for equal fees, but differing fees require considering combinations of requests. The weighted-interval dynamic program returns the maximum revenue, and brute force provides a useful check for small cases.
